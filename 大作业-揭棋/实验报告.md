# 揭棋对弈程序实验报告

## 一、题目

揭棋对弈程序设计。

本组选择实现大作业中的第一部分：**设计一个揭棋对弈程序**。程序支持两个客户端通过服务器进行真人对弈，服务器与客户端通过 TCP Socket 和 JSON 消息通信，服务器负责回合控制、走法校验、随机翻子、超时判断、棋谱记录以及跨组协议兼容。

## 二、小组成员与分工

本组共两名成员，请提交前将“成员A / 成员B”替换为真实姓名。

| 成员 | 主要分工 | 贡献度 |
| --- | --- | --- |
| 成员A | 需求分析、总体架构设计、服务器通信、回合控制、超时处理、跨组互操作协议兼容、联调测试 | 55% |
| 成员B | 棋盘与棋子模型、揭棋走法规则、图形界面、AI 辅助测试、实验报告整理、验收演示准备 | 45% |

两名成员共同参与了需求讨论、AI 辅助设计、代码调试和验收测试。

## 三、需求分析

根据题目要求，本程序需要完成以下功能：

1. 支持两个客户端连接同一个服务器进行真人对弈。
2. 服务器和客户端通过网络通信，通信内容采用 JSON 格式。
3. 服务器能够禁止错误着法，非法走子不能改变棋盘状态。
4. 揭棋暗子由服务器随机决定真实棋子类型，客户端不能伪造翻子结果。
5. 服务器负责回合控制，保证未轮到的一方不能走子。
6. 服务器以服务器端时间为准判断超时。
7. 支持棋谱记录，记录每一步 source、destination 和翻子结果。
8. 支持图形化客户端，方便验收时进行可视化交互。
9. 支持跨组互操作，即本组服务器能够兼容其他组客户端，本组客户端也尽量兼容其他组服务器。

本程序主要实现“对弈程序”，不是以 AI 博弈作为主要方向。AI 相关类用于辅助搜索、测试和扩展，不作为本次核心验收点。

## 四、总体设计

系统采用面向对象设计，分为四个层次：

1. 通信层：`GameServer`、`ClientHandler`、`ConsoleClient`、`JieQiGUI`。
2. 协议层：`JsonUtil`、`ProtocolUtil`、`Move`。
3. 业务层：`Game`、`MoveValidator`、`MoveResult`。
4. 领域模型层：`Board`、`Piece`、`Position`、`PieceType`、`Color`。

服务器端负责游戏权威状态，客户端只负责发送走子请求和显示结果。这样可以避免客户端作弊，也方便不同小组之间进行互操作。

## 五、核心类说明

`GameServer`：服务器入口。负责监听端口、接受客户端连接、创建对局房间，并启动超时监控线程。

`ClientHandler`：每个客户端连接对应一个处理线程。负责接收 JSON 消息、调用 `Game` 执行走子，并向双方广播结果。

`Game`：表示一局棋。负责当前回合、胜负状态、超时、和棋、棋谱保存等核心对局逻辑。

`Board`：表示棋盘。负责棋子初始化、棋子移动、查找将帅、复制棋盘和生成棋盘 JSON。

`Piece`：表示棋子。包含颜色、原始位置对应的棋子类型、真实类型、是否明子。

`Move`：表示一步棋。包含 `source`、`destination`、`type`、`isFlip`、`turnStartTime` 等信息，同时兼容公共协议的 `fromX/fromY/toX/toY`。

`MoveValidator`：负责校验车、马、炮、兵、士、象、将帅等棋子的走法是否合法。

`JieQiGUI`：图形化客户端。支持填写服务器 IP 和端口，连接服务器后通过点击棋盘进行走子或翻子。

`ProtocolUtil`：协议兼容辅助类。用于生成同时包含本组字段和公共字段的 JSON 消息。

## 六、关键实现

### 1. 揭棋暗子机制

开局时，双方除了将/帅为明子外，其余棋子均为暗子。暗子保留两个类型：

- 原始位置类型：用于暗子第一次移动前判断走法。
- 真实类型：由服务器随机生成，暗子移动或原地翻开后显示。

暗子移动成功后，服务器揭示真实类型，并通过 `flipResult` 广播给双方客户端。

### 2. 服务器权威校验

客户端发送的只是走子请求。服务器收到后进行以下检查：

1. 是否轮到该颜色走棋。
2. 起点是否有本方棋子。
3. 目标位置是否允许进入。
4. 当前棋子的走法是否合法。
5. 是否超时。

如果不合法，服务器返回：

```json
{"messageType":"moveResult","success":false,"valid":false}
```

棋盘状态不会改变。

### 3. TCP Socket 与 JSON 通信

程序使用 TCP Socket 通信，每条消息是一行 JSON 文本。主要消息类型包括：

- `gameStart`
- `move`
- `moveResult`
- `yourTurn`
- `gameOver`
- `ping`
- `pong`
- `Resign`

使用 JSON 的好处是结构清楚，便于不同小组之间约定字段并进行互操作。

### 4. 图形化交互

`JieQiGUI` 提供图形棋盘界面。用户可以：

1. 输入服务器 IP 和端口。
2. 点击 `Connect` 连接服务器。
3. 在自己的回合点击棋子和目标位置完成移动。
4. 点击同一个暗子位置完成原地翻子。
5. 点击 `Resign` 认输。

验收时可以用两个 GUI 客户端连接同一服务器进行可视化演示。

### 5. 跨组互操作

题目要求“服务器和客户端可以互操作，比如第一组的服务器可以连接第二组的客户端”。为满足该要求，本程序做了协议兼容：

1. 服务器既支持本组原有格式：

```json
{"messageType":"move","source":"a3","destination":"a4","isFlip":false}
```

也支持公共接口格式：

```json
{"messageType":"move","fromX":"a","fromY":6,"toX":"a","toY":5,"isFlip":false}
```

2. 客户端发送走子时同时带两套字段：

```json
{
  "messageType": "move",
  "source": "a3",
  "destination": "a4",
  "fromX": "a",
  "fromY": 6,
  "toX": "a",
  "toY": 5,
  "isFlip": false
}
```

3. 服务器返回 `moveResult` 时同时包含嵌套 `move`、平铺坐标字段、`board` 和 `boardArray`，方便其他组客户端解析。

4. 服务器对 `Login`、`register`、`startMatch`、`Ready`、`requestFirstHand`、`ping`、`Resign` 等消息做了兼容处理，避免其他组客户端连接后因消息类型不同直接失败。

## 七、利用 AI 设计较大规模程序的方法

题目要求必须使用 AI 辅助分析设计、编程测试。本项目采用“人机协作、分模块迭代”的方式，而不是一次性让 AI 生成全部程序。

### 1. 需求分析阶段

先将题目要求输入给 AI，让 AI 帮助整理功能点、边界条件和可能遗漏的问题。经过人工确认后，确定本组实现“揭棋对弈程序”方向，而不是 AI 博弈方向。

AI 辅助整理出的关键需求包括：

- 服务器负责权威判断。
- 客户端只提交走子意图。
- 暗子真实类型必须由服务器决定。
- 每一步需要通过 JSON 传输。
- 需要考虑跨组协议兼容。

人工负责判断哪些功能是必做，哪些功能属于可选或扩展。

### 2. 架构设计阶段

在 AI 辅助下，将系统拆成通信层、协议层、业务层和领域模型层。这样可以避免所有逻辑写在一个类里，便于调试和扩展。

AI 给出了初步类划分后，人工根据课程要求进行了调整，确保领域类超过 5 个，并且类职责清晰。

### 3. 任务拆分阶段

没有一次性生成完整程序，而是按以下小任务逐步完成：

1. 定义 `Color`、`PieceType`、`Position`、`Piece` 等基础模型。
2. 实现 `Board` 初始化和暗子随机分配。
3. 实现 `Move` 和 JSON 协议解析。
4. 实现 `MoveValidator` 走法校验。
5. 实现 `Game` 回合与胜负控制。
6. 实现 `GameServer` 和 `ClientHandler`。
7. 实现命令行客户端 `ConsoleClient`。
8. 实现图形化客户端 `JieQiGUI`。
9. 增加跨组互操作兼容。
10. 编写测试类和实验报告。

每个任务规模较小，便于编译、运行和定位错误。

### 4. 测试驱动与迭代修正

开发过程中使用 AI 辅助分析编译错误和运行结果。例如：

- 修正 Java 8 兼容问题。
- 修正原地翻子被误判为“吃自己棋子”的问题。
- 修正服务器端口占用导致无法重启的问题。
- 修正跨组公共字段 `fromX/fromY/toX/toY` 的兼容问题。
- 增加 `InteropProtocolTest` 验证服务器可接收公共协议格式。

测试通过后再继续扩展下一部分功能。

### 5. 人工把控内容

AI 主要负责辅助设计、生成代码和解释错误。以下内容由小组成员人工决定：

- 选择实现“对弈程序”方向。
- 确定服务器为权威状态维护者。
- 确定图形化验收方式。
- 确定跨组互操作需要兼容公共协议字段。
- 对最终运行结果和实验报告进行检查。

因此，AI 在本项目中相当于高级结对程序员，而不是完全替代小组成员。

## 八、测试情况

### 1. 编译测试

执行：

```powershell
javac -encoding UTF-8 -d bin src\*.java
```

项目可以成功编译。

### 2. 本机双客户端测试

启动服务器：

```powershell
java -cp bin GameServer 8887
```

启动两个 GUI 客户端：

```powershell
java -cp bin JieQiGUI localhost 8887 connect
java -cp bin JieQiGUI localhost 8887 connect
```

测试内容：

1. 两个客户端成功连接。
2. 第一个客户端为红方，第二个客户端为黑方。
3. 红方先手。
4. 合法走子返回 `success:true`、`valid:true`。
5. 非法走子返回 `success:false`、`valid:false`。
6. 暗子移动后服务器返回 `flipResult`。
7. 原地翻子作为一个回合。
8. 认输后双方收到 `gameOver`。

### 3. 跨组互操作测试

执行：

```powershell
java -cp bin InteropProtocolTest
```

测试类模拟外部客户端，只发送公共接口字段：

```json
{"messageType":"move","fromX":"a","fromY":6,"toX":"a","toY":5,"isFlip":false}
```

服务器能够正确接收并返回 `moveResult`，说明具备跨组互操作能力。

### 4. 网络互连测试

服务器启动后会输出本机可用 IP，例如：

```text
Realtek WiFi Adapter: 10.21.191.36:8887
```

其他组客户端可使用该 IP 和端口连接。实际互连时需要注意 Windows 防火墙允许 Java 访问网络，并确保双方处于同一局域网或热点环境。

## 九、运行与验收方式

### 1. 本组服务器 + 本组 GUI 客户端

```powershell
java -cp bin GameServer 8887
java -cp bin JieQiGUI localhost 8887 connect
java -cp bin JieQiGUI localhost 8887 connect
```

### 2. 本组服务器 + 其他组客户端

本组运行：

```powershell
java -cp bin GameServer 8887
```

将服务器输出的真实局域网 IP 和端口发给其他组，例如：

```text
10.21.191.36:8887
```

其他组客户端连接该地址即可。

### 3. 本组 GUI 客户端 + 其他组服务器

```powershell
java -cp bin JieQiGUI 对方IP 对方端口 connect
```

例如：

```powershell
java -cp bin JieQiGUI 10.21.191.50 8887 connect
```

## 十、存在的不足与改进方向

1. 当前客户端界面以功能可用为主，美观程度有限。
2. 跨组互操作已兼容主要公共字段，但不同小组如果自定义了额外字段，仍可能需要现场调整。
3. 将死、长将、长捉等复杂规则已做部分支持，但仍可继续完善。
4. 当前 AI 不是主要功能，后续可进一步完善评估函数和搜索算法。
5. 可以继续扩展为账号登录、匹配大厅、多局持久房间等功能。

## 十一、总结

本项目完成了揭棋对弈程序的核心功能，体现了面向对象程序设计中的封装、继承、多对象协作、网络通信、图形界面和协议兼容。程序支持两个客户端通过服务器真人对弈，服务器负责权威校验、随机翻子、回合控制和结果广播。

在开发过程中，本组按照题目中“利用 AI 设计较大规模程序的方法”的要求，先进行需求分析和架构设计，再拆分为多个可验证的小任务，逐步实现、编译、测试和修正。最终程序可以在 Eclipse 或命令行中运行，能够进行图形化验收展示，并具备与其他小组服务器/客户端互操作的基础能力。
